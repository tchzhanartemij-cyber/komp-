### R1 — P1 / потеря пользовательского ввода: ошибка сохранения стирает черновик
Версия: production task7 clone и candidate, browser подтверждено на обоих.

Дальше: await результат mutation, reset/close только после успеха, preserve draft, disable double-submit, inline actionable error.

### R3 — P2 / исходная жалоба: крестик «Закрыть» Памяти не скрывает панель

Expected по жалобе: закрыть/скрыть карточку-панель, освободить место графу. Escape должен давать согласованное закрытие.

### R5 — P2 / потеря черновика Памяти после blur и обновления

Repro: выбрать страницу, набрать новый факт без отправки; кликнуть поиск, затем внести несвязанную запись через другую форму/Telegram и дождаться polling refresh (в QA внешний update синтетически через /api/notes/add, затем load()).

Дальше: map drafts по entity/form, сохранять независимо от activeElement; restore selection/caret только при необходимости, не пересоздавать форму при нерелевантных данных.

### R6 — P2 / устойчивость: polling /api/data перекрывается на медленном соединении
Версия: production clone browser с искусственной задержкой; candidate тот же load interval, agent refresh отдельно защищен agentRefreshing.
Repro: задержать /api/data на 13 секунд при видимой странице и интервале 10 секунд, 35-секундное окно.
Expected: single-flight, отмена устаревшего запроса или polling после завершения.
Actual: максимум 2 одновременно незавершенных data requests; 4 completed после возврата к нормальному режиму, pending=0. При обычной локальной задержке накопления не обнаружено. Это fault-injection resilience, НЕ утверждение о реальном production лаге.
Риск: лишняя нагрузка, устаревший ответ может перерисовать свежие данные, отсутствуют timeout/backoff. Не доказан реальный stale overwrite.
Дальше: inFlight guard/AbortController + monotonic revision, timeout, пауза/backoff при ошибках. Agent candidate refresh уже single-flight — этот подход распространить на data.
