# Task 12: единая «Переписка» (Telegram + Сводка + агенты)

## Каноническая сессия и интерфейсы

Одна сессия OpenClaw — та, в которую пишет owner-чат Telegram. Оператор задаёт
её явно: `SVODKA_CANONICAL_SESSION` (`main` → `agent:<SVODKA_AGENT_ID>:main`
или точный `agent:<id>:<key>`; `subagent:`/`cron:`/`acp:` запрещены) и
включает раздел `SVODKA_WORKSPACE_ENABLED=1`. Без них вкладка показывает точную
причину, ввод и кнопки выключены. Панель не угадывает ключ и не читает конфиг.

Все вызовы только с бэкенда, тем же файлом токена 0600, что агент задачи 9/11,
на loopback-адрес из `SVODKA_AGENT_URL`. Браузер токен не получает.

| Что | Поддерживаемый интерфейс Gateway |
| --- | --- |
| История | `POST /tools/invoke` → `sessions_history` (`includeTools:false`, `limit≤50`, `offset/nextOffset`) |
| Сессия и субагенты | `POST /tools/invoke` → `sessions_list` (фильтр: канонический ключ и его дети) |
| Отправка | `POST /v1/responses` + `x-openclaw-session-key: <канон>` (без поля `user`) |

Белый список инструментов в коде — только эти два. Никакого второго бота,
скрейпинга, CLI или WebSocket-RPC. Тело ошибок Gateway не логируется и не
возвращается — только код и русское сообщение.

При заданной канонической сессии `/api/agent/send` (вкладка «Агент», голос
задачи 11) тоже идёт в неё: текст, голос и Telegram — одна история.

## История

`GET /api/workspace/history?offset=&limit=` — ограниченный хвост (30) и
«Загрузить раньше» по `next_offset`; полная выгрузка в браузер не делается.
Показываются только `user`/`assistant`; system/tool скрыты и посчитаны.
Удаляются `<think>`, `<thinking>`, `<reasoning>`, `<relevant-memories>`,
XML вызовов инструментов, управляющие токены; секретоподобное → `***`.
Вложения — метки без данных. Источник: `Сводка` по тегу `[Сводка:<request>]`,
иначе канал сессии (`telegram`), ответы — `агент`. Пометки: пропуск в истории
(`truncated/droppedMessages/windowReset`), скрытое шлюзом, изменено/удалено —
только если Gateway отдаёт такие поля (в текущем `chat.history` их обычно нет).
Хвост кэшируется на 2 с — несколько вкладок не умножают нагрузку.

## Живые обновления

Честный bounded poll: хвост раз в 4 с, только при видимой вкладке «Переписка»,
backoff до 30 с, мгновенный повтор по `online`. Статус «обновлено ЧЧ:ММ:СС» /
«соединение потеряно, повтор через N с». Слияние по id сообщения (dedupe),
порядок — порядок транскрипта. SSE/WebSocket подписка (`sessions.messages.subscribe`)
есть только в WS-протоколе Gateway и требует отдельного решения оператора.
Стриминг частичного ответа в «Переписке» не показывается (только сохранённые
сообщения); голосовая панель задачи 11 по-прежнему читает `run.output`.

## Отправка, идемпотентность, эхо

`POST /api/workspace/send {text, request}`: request id создаётся один раз на
черновик, повтор после сетевой ошибки шлёт тот же объект → сервер возвращает
существующий запуск (`duplicate:true`), второго вызова нет. Текст получает
origin-тег `[Сводка:<request>]`; локальная плашка «ожидает подтверждения»
исчезает, когда сообщение с этим тегом появилось в истории. Ответ на запрос из
Сводки не отправляется в Telegram (Responses API не доставляет в канал) —
эха и двойного ответа нет; в Telegram-клиенте эта реплика не видна, только в
общей истории сессии.

## Уточнение запроса (ревизии)

«Уточнить» → черновик в `workspace.sqlite3` (исходник, новая редакция, request).
Сохранение ничего не отправляет. Явная кнопка «Отправить изменённый запрос» с
предупреждением: выполненные действия и сообщения не отменяются, сообщение в
Telegram не редактируется — уходит новая связанная инструкция с исходным
текстом и id. Повторная отправка того же черновика идемпотентна. История
OpenClaw не переписывается, автоматического replay нет.

## Задачи

Лента: запуски панели, очередь кодера (без названий/путей), каноническая
сессия и субагенты. Статусы: в очереди / выполняется / ждёт решения владельца
(`question`) / готово / ошибка / отменено / неизвестно / устарело (running без
обновлений > 15 мин). `waiting_limit` — «в очереди». Модель — только если она
пришла в данных. Процентов и стадий по таймеру нет. «Отменить» всегда
disabled с причиной: `sessions.abort` доступен только через WS-RPC, а
остановка UI не отменяет выполнение.

## Безопасность

Все `/api/workspace*` — после обычной авторизации cookie/ссылки (401),
требуют защищённую панель (503 иначе); POST — `application/json` (415) и
same-origin (403). Только сессия владельца и её дети; групповые и чужие сессии
отфильтрованы.
